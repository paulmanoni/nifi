nifi

An embeddable Go library for moving databases. Build a migration on a canvas, run it in resumable chunks, and — when the source keeps changing — have the same flow follow it afterwards. It mounts inside a service you already have, as one http.Handler.

Not Apache NiFi, and not from the Apache Software Foundation. The interface is deliberately modelled on Apache NiFi's, because that is the shape an operator already knows — but this shares none of its code, runs none of its processors and reads none of its flow definitions. Apache®, Apache NiFi, NiFi and the feather logo are trademarks of the Apache Software Foundation; this project is not endorsed by or affiliated with it. Looking for Apache NiFi? It is at nifi.apache.org.

It moves MySQL → PostgreSQL and PostgreSQL → PostgreSQL.

You getWhich means
A canvasSources, transforms and sinks with generated forms, and a preview of real rows at any node before anything runs.
An engineParallel key-range chunks, bounded queues with back-pressure, PostgreSQL COPY through a staging table.
Exact restartsA chunk is checkpointed only once every batch from it is written, so a stopped run resumes on the first row it did not finish.
Somewhere for bad rowsA row the destination refuses is found, set aside with its reason, and can be replayed once the flow is fixed.
One binaryui/dist ships in the module: no Node at build or run time for anything that depends on this.

Install and embed

go get github.com/paulmanoni/nifi@v0.2.0

The whole thing is one handler. Mount it wherever you like:

package main

import (
    "context"
    "log"
    "net/http"
    "os"

    "github.com/paulmanoni/nifi"
)

func main() {
    engine, err := nifi.New(nifi.Config{
        Title:    "Data Flows",
        DataPath: "var/nifi.db",           // management state (SQLite)
        Connections: []nifi.Connection{
            {ID: "legacy", Driver: "mysql", Host: "10.0.0.5", User: "ro",
             Password: os.Getenv("LEGACY_PW"), Database: "app"},
            {ID: "main", Driver: "postgres", Host: "localhost", User: "app",
             Password: os.Getenv("PG_PW"), Database: "app",
             Description: "primary Postgres"},
        },
    })
    if err != nil {
        log.Fatal(err)
    }
    defer engine.Close(context.Background())

    http.Handle("/flows/", http.StripPrefix("/flows", engine.Handler()))
    log.Fatal(http.ListenAndServe(":8080", nil))
}

That handler serves the UI, the JSON API and the live run stream. State — flows, runs, checkpoints, bulletins, dead letters — lives in the SQLite file at DataPath.

Or standalone

There is a command for trying it without writing any Go:

go run github.com/paulmanoni/nifi/cmd/nifi@v0.2.0 -addr :8090 -config connections.json

Connections

A connection is a database flows read from or write to. There are two ways to have one, and both are listed together.

Declared in codeAdded in the UI
Lives innifi.Config.Connectionsthe state file
In the UIlisted, lockededitable, deletable
Credentialsthe host's own configthe state file

What the host declared always wins. A stored connection can never take over an id the application believes it owns: the API refuses to write or delete one, and the resolver checks code first. That keeps exactly one meaning per id.

Passwords are write-only. They are never returned by the API, and an edit that leaves the field empty keeps the stored one rather than blanking it by omission.

A password added through the UI sits in the state file in plain text. Treat that file as a secret — it already holds run history and dead-lettered rows. Where that is not good enough, declare the connection in code and read its password from wherever your app keeps secrets.

Inside a nexus app

A separate module mounts the whole thing as a nexus module, taking its connections from nexus.toml's [databases.*] blocks: 

go get github.com/paulmanoni/nifi/nexusnifi@v0.1.0
var Module = nexusnifi.Module(nexusnifi.Config{
    Path:      "/migrations/flows",
    Databases: []string{"legacy", "main"},
    Engine:    nifi.Config{DataPath: "var/nifi.db"},
    Options:   []nexus.RestOption{auth.Required()},
    Permissions: map[nifi.Action]string{
        nifi.ActionEdit: "change_migration",
        nifi.ActionRun:  "run_migration",
        nifi.ActionData: "view_migration_data",
    },
})

It is a module of its own so that nothing depending on the core library pulls nexus in. Use nexusnifi.Routes(cfg) instead to spread the routes into an existing module, so its own path prefix applies.

Authorization

Four permissions gate everything:

ActionCovers
ActionViewSee flows, runs, progress and bulletins.
ActionEditCreate, change, duplicate and delete flows — and stored connections.
ActionRunStart, pause, resume and stop runs.
ActionDataRead database contents: table browsing, previews, connection tests, dead-lettered rows.

Hand it your own check, and it never has to know how your app authenticates:

nifi.Config{
    Authorize: func(r *http.Request, a nifi.Action) error {
        u := userFrom(r)
        if u == nil {
            return nifi.ErrUnauthenticated       // 401
        }
        if !u.Can(string(a)) {
            return nifi.ErrForbidden             // 403
        }
        return nil
    },
}

Without one, Config.Users gives built-in accounts with per-user actions, and Config.BasicAuth generates an admin password on first start, printed to the console and kept in the state file. Leave all three unset only behind a mount you have already protected.

One source can read many tables and send each down its own path: a connection carries only the tables you name, so users can take one branch and orders another.

Expressions

Columns, filters and computed values are written as expressions over the row — lower(trim(email)), concat(first_name, ' ', last_name), coalesce(x, 0). The editor lists every function with its arguments and help, including any the host adds.

table is the current table's name, so one node can behave differently per table: table == "users" ? upper(name) : name.

Scripts

When the GUI steps cannot say it, a Python Script node runs Starlark — a Python dialect interpreted in pure Go, sandboxed, with no CGO. 

def transform(row):
    if not row["email"]:
        return None                     # drop the row
    row["domain"] = row["email"].split("@")[-1]
    return row                          # or a list of dicts, to fan out

Set row["_table"] to send a row to a different table. A script that adds or drops rows cannot carry a change feed through it, because it no longer says which row is which — the run says so rather than guessing.

Scripts cost about 1.2µs per row against 0.6µs for an expression and 0.05µs for hand-written Go: worth knowing, rarely worth worrying about next to the database.

Parameters

Write #{name} in any setting — a target schema, a row filter, a file path — and it is replaced when the flow runs, so one flow serves several environments. Parameters live in the store, or come fixed from nifi.Config.Parameters; a sensitive one is never returned by the API. A flow naming a parameter nobody defined fails validation, saying which.

Schedules and folders

A flow can run itself: a cron expression (0 2 * * *) or a shorthand (@hourly, @every 30m). A flow still running when its next time comes round is skipped, so slow runs never pile up, and an instance that was down starts it once on return rather than replaying every missed slot.

Flows can depend on other flows, and Run all starts them in dependency order. Folders group the list; every save is kept in a history that can be compared and restored.

What a run does

Rows travel in batches along connections with bounded queues, so a slow destination pushes back on the source rather than filling memory. The run page shows per-node throughput, what each queue is holding, the bulletins, and every row that failed.

Chunks, resume and dead letters

  • Chunking. A single integer primary key is split into ranges read in parallel. Composite or text keys page with keyset reads. A table with no key streams in one pass, flagged as not resumable.
  • Exactly-once bookkeeping. Every batch holds a ticket for its chunk; the chunk is checkpointed only after every batch derived from it is committed or deliberately dropped. Resume skips committed chunks.
  • Writes. merge COPYs into a temporary staging table then runs INSERT … ON CONFLICT DO UPDATE, so a re-applied chunk is harmless. copy is fastest for empty targets and becomes merge_ignore on resume.
  • Bad rows. The row is found from the COPY error, or by bisecting the batch, then dead-lettered with its reason while the rest commits. MaxErrors stops a run that is failing wholesale.
  • Replay. Dead letters can be fed back into the node that failed on them, so a fix is checked against the rows that actually broke.

Following changes

A flow does not have to read its source once and stop. Give it a Table Changes source and it keeps going: rows are written as they appear and removed as they are deleted, and the run ends only when you stop it.

It needs one column per table that moves whenever a row is written — the updated_at every ORM already maintains. Rows are read in (updated_at, primary key) order, so nothing is missed and nothing is read twice, and the position is remembered against the flow: stop it, deploy, start it again, and it carries on.

Turn on the destination's Apply changes from a feed. A changed row then overwrites the matching row and a deleted one is removed, in the order the changes arrived. It is a setting beside the write mode, not one of its values, because the two answer different questions: the mode governs the first load, while a change is not a duplicate and always overwrites.

Load it, then follow it — in one run

Put both sources in the same flow. The feed fixes its position before anything runs, then waits until the load has finished before emitting — so the load is not racing the changes that would overtake it, and a row changed while it was loading is still applied.

A source that polls cannot see a hard DELETE — the row is simply gone. Soft deletes it can: fill in A row is deleted when with an expression such as deleted_at != nil. To follow hard deletes, give the engine a source that reads the database's replication log; see Extending.

A node from a Go function

Writing a Handler by hand means the engine can run your code but knows nothing else about it. nifi.Mapper is the same node declared instead of assembled: the input type says how to read a row, the output type says what the node emits. 

type User struct {
    ID     int64  `nifi:"id"`
    Name   string `nifi:"full_name"`
    Email  *string
    Secret string `nifi:"-"`      // not written
}

nifi.Config{Processors: []nifi.Processor{
    nifi.Mapper[nifi.Row, User]{
        Type: "app.map_users", Label: "Map users", Icon: "user",
        PrimaryKey: []string{"id"},
        Properties: []nifi.Property{{Key: "domain", Label: "Email domain", Kind: "string"}},
        Open: func(s nifi.Settings) (nifi.MapFunc[nifi.Row, User], func(), error) {
            domain := s.String("domain")
            return func(ctx context.Context, in nifi.Row) (*User, error) {
                name, _ := in["name"].(string)
                if name == "" {
                    return nil, nil                 // drop the row
                }
                return &User{ID: in["id"].(int64), Name: name}, nil
            }, nil, nil
        },
    }.Processor(),
}}
  • nil drops a row, an error fails only that row — it goes to "failure" with the message while the rest of the batch goes on.
  • The output columns come from the type. Field → column by the nifi tag, else db, else json, else snake_case; - omits; embedded structs flatten; a nil pointer is NULL.
  • The input is nifi.Row (column → value) or a struct, filled from the incoming columns by name.
  • Operations follow their own row. A mapping that drops rows makes position stop meaning identity; the library keeps each output row's insert/update/delete attached to the input row it came from.
Open must not touch the world. It is called whenever the node is built — which includes checking a flow and reading its schema, not only running one. Read settings there and fail on one that cannot work, but put connections and caches behind the first row (a sync.Once inside the returned function), so that pressing Validate changes nothing.

Sources, and streaming ones

Sources: []nifi.Source{{
    Type: "app.binlog", Label: "Replication log", Icon: "radio", Streaming: true,
    New: func(s nifi.Settings) (nifi.Reader, error) { return &binlogReader{s: s}, nil },
}}

Streaming: true means Read blocks until the run is stopped, and the run is live. Tag each row with what happened to it — batch.Append(row, record.Delete) — and keep your position with s.Remember/s.Recall, which is stored against the flow so the next run continues. Write the position from the batch's record.Ticket callback, so it only moves once those rows are safely written.

Declaring a schema

A node that implements Schematic stops being opaque:

func (h *myHandler) Columns(in []record.Column) ([]record.Column, error)

The designer then shows its output without running it, and the schema keeps flowing through it when the sample it is given has no rows — which is exactly when a node that renders from a schema tends to report fewer columns than it really writes. A Mapper implements it already, from its output type.

Writing a GORM model

Migrating into tables a GORM application already writes to means matching what it writes, and "every field, as it stands" is not that. GORM applies rules on Create: a zero field takes its default tag, a zero CreatedAt/UpdatedAt becomes now, and a column whose default lives in the database is left out of the statement entirely while every row leaves it zero — so the database applies it per row. 

go get github.com/paulmanoni/nifi/gormx@v0.1.0
gormx.Mapper(nifi.Mapper[nifi.Row, User]{
    Type: "app.map_users", Label: "Map users", Map: mapUser,
}).Processor()

It fills in the node's columns, primary key and rendering from the model's own schema, and needs no connection — only the naming strategy, which you pass with gormx.Naming if your app configures one. gormx.Copy() switches to what a bulk COPY that ignores conflicts does instead. gormx.Value renders a single value the same way, for wherever a host computes one itself.

GORM promotes an embedded struct's fields only when its type is exported. Embed an unexported one and its columns — including the primary key — quietly disappear. gormx does the same, because its job is to match GORM.

Expression functions

The cheapest way to reach code: expose one function, and the rest of the mapping stays on the canvas.

Functions: []nifi.Function{{
    Name: "normalizePhone", Args: "value", Help: "+255 form of a local number",
    Fn: func(a ...any) (any, error) { return phone.Normalize(fmt.Sprint(a[0])), nil },
}}

Arguments arrive as row values and the result goes back as one; an error fails the row, which becomes a dead letter with the message. They are listed in the expression editor beside the built-ins.

Seeding flows

Ship flows with the application and have them appear on first start: nifi.Config.SeedFlows takes an fs.FS of one JSON file per flow. A missing flow is created; a flow whose file version is newer than the last one applied is overwritten, and edits made in the UI are kept until that version is raised. 

{"id": "mig_regions", "version": 2, "name": "regions", "folder": "reference",
 "dependsOn": ["mig_countries"], "graph": {"nodes": [], "edges": []}}

Config.BeforeRun and Config.AfterRun bracket every run, with the flow and the run's id — for preparing a target before it loads, and for recording the outcome where the host keeps that.

HTTP API

Everything the UI does is a documented JSON endpoint under the mount path, so the engine can be driven from a script or another service. The full reference — every route, payload and type — is in API.md. A sample:

RouteDoes
GET /api/flowsList flows with their latest run.
POST /api/flows/:id/runsStart a run; {resume: true} continues an unfinished one.
GET /api/runs/:id/eventsServer-sent events: progress, bulletins, completion.
POST /api/flows/previewRun sample rows through the flow up to a node, writing nothing.
PUT /api/connections/:idCreate or replace a stored connection.
GET /api/processorsThe processor catalog, including anything the host added.
